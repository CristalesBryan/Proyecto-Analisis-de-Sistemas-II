2. Introducción
El presente documento describe el Caso de Uso CU-04: Actualizar Seguimiento del Caso del Sistema de Quejas, Reclamos, Denuncias y Sugerencias (QRDS) Municipal. Este caso de uso implementa el módulo de Seguimiento definido en los Términos de Referencia (TDR) y garantiza la trazabilidad operativa mientras el caso se encuentra activo.
A diferencia de CU-03 (Gestionar Caso), que se concentra en la asignación de agentes y en las transiciones de estado del ciclo de vida, CU-04 se enfoca en el registro continuo de avances: actualizaciones de progreso, mensajes visibles para el ciudadano, control de plazos de respuesta, escalamiento por vencimiento y evidencias de seguimiento. Cada actualización alimenta la línea de tiempo del caso y queda registrada de forma inmutable en la bitácora de auditoría.
Este módulo es crítico para la transparencia institucional: el ciudadano puede consultar vía código de seguimiento (CU-07 / portal público) el progreso de su caso sin exponer información interna sensible.
3. Objetivo
Permitir que el agente asignado (y roles superiores) registren actualizaciones de seguimiento sobre un caso en estado EN_REVISION o EN_PROCESO, diferenciando entre notas internas y actualizaciones públicas, controlar el cumplimiento de plazos según el tipo de caso, notificar al ciudadano cuando corresponda y dejar evidencia auditable de cada avance.
4. Definición del Caso de Uso
4.1 Actores
ID
Actor
Descripción
AC-01
Agente / Funcionario
Usuario con rol AGENTE. Registra avances y actualizaciones públicas/internas únicamente en los casos asignados a él.
AC-02
Supervisor
Usuario con rol SUPERVISOR. Puede registrar seguimientos en casos de su área, escalar casos y prorrogar plazos con justificación.
AC-03
Administrador
Usuario con rol ADMIN. Tiene control total sobre seguimientos, plazos y escalamientos de cualquier caso.
AC-04
Ciudadano
Consulta el progreso público del caso mediante el código de seguimiento (consumidor de actualizaciones públicas). No escribe seguimientos.
AC-05
Sistema QRDS
Valida permisos, calcula plazos, envía notificaciones, actualiza la línea de tiempo y registra eventos en bitácora.
4.2 Precondiciones
El usuario interno debe estar autenticado (CU-01) con token JWT válido.
El caso debe existir en BD y encontrarse en estado EN_REVISION o EN_PROCESO. [RN-01]
Para el Agente: el caso debe estar asignado a su usuario (agente_asignado_id). Supervisor/Admin según reglas de visibilidad de CU-03.
La tabla de plazos por tipo de caso debe estar configurada (Queja: 15 días hábiles, Reclamo: 20, Denuncia: 30, Sugerencia: 30).
El módulo de notificaciones y bitácoras debe estar operativo.
PostgreSQL debe estar disponible con las tablas: casos, seguimientos_caso, bitacora_casos, documentos_caso, usuarios.

6. Flujos Alternos
Código
Nombre
Descripción
FA-01
Actualización Solo Interna
El usuario elige tipo INTERNA. El registro no es visible en la consulta pública (CU-07). No se ofrece notificar al ciudadano (checkbox deshabilitado). Queda en bitácora y en la línea de tiempo interna.
FA-02
Adjuntar Evidencia de Seguimiento
El usuario adjunta un archivo (PDF, JPG, PNG, DOCX ≤ 5 MB). El sistema valida formato/tamaño. Si falla, muestra error por archivo y no guarda el seguimiento hasta corregir o quitar el adjunto. La descarga posterior se registra en bitácora (TDR).
FA-03
Caso en Estado No Válido
El caso está RESUELTO, CERRADO o ANULADO. El sistema bloquea nuevas actualizaciones (excepto Admin puede agregar nota histórica INTERNA con justificación excepcional). Muestra: No se pueden registrar seguimientos en casos finalizados.
FA-04
Sin Permiso Sobre el Caso
Un AGENTE intenta registrar seguimiento en un caso no asignado. HTTP 403. Mensaje: No tiene permisos para actualizar este caso. Intento registrado en bitácora.
FA-05
Fallo al Enviar Notificación
El seguimiento ya se guardó. El SMTP falla. Se muestra aviso: Seguimiento guardado, pero no fue posible notificar al ciudadano. Se registra fallo en log/bitácora de notificaciones. El ciudadano aún verá el avance al consultar el portal.
FA-06
Alerta de Plazo por Vencer
Al abrir el caso, el sistema detecta que restan ≤ 3 días hábiles. Muestra banner amarillo: Plazo próximo a vencer. El Supervisor/Admin puede prorrogar (FA-07).
FA-07
Prorrogar Plazo
Supervisor o Admin solicita prórroga: días hábiles adicionales (1-15) + justificación ≥ 20 caracteres. El sistema recalcula fecha_limite_respuesta, registra PRORROGA_PLAZO en bitácora y opcionalmente notifica al ciudadano.
FA-08
Escalamiento por Vencimiento
Job programado (o acción manual del Supervisor) detecta plazo vencido sin resolución. Marca PRIORIDAD=ALTA / escalado=true, notifica al Supervisor del área y registra ESCALAMIENTO en bitácora. No cambia el estado del ciclo de vida automáticamente.
FA-09
Edición No Permitida
El usuario intenta modificar o eliminar un seguimiento ya registrado. El sistema lo impide: los seguimientos son inmutables (solo INSERT). Para corregir, se registra un nuevo seguimiento de tipo CORRECCIÓN que referencia al anterior. [RN-08]
FA-10
Derivar a Resolución
Desde el panel de seguimiento, el agente selecciona Proceder a Resolver (CU-05). El sistema no resuelve aquí; redirige al flujo de resolución formal manteniendo el historial de seguimientos intacto.
7. Postcondiciones
Quedó registrado al menos un nuevo seguimiento asociado al caso (público y/o interno).
fecha_ultima_actualizacion (y avance_porcentaje si aplica) del caso fueron actualizados.
Si la actualización fue pública y el ciudadano consultó/recibió correo, conoce el avance sin ver notas internas.
El evento quedó en bitácora de forma inmutable.
Si hubo prórroga o escalamiento, el plazo/prioridad quedó actualizado y auditado.
El caso permanece listo para continuar en CU-04 (más avances), CU-05 (Resolver) o CU-03 (cambio de estado si aplica).

9. Reglas de Negocio
Código
Descripción
RN-01
Solo se permiten nuevos seguimientos cuando el estado del caso es EN_REVISION o EN_PROCESO. Excepción: Admin puede agregar nota INTERNA en RESUELTO/CERRADO/ANULADO con justificación ≥ 20 caracteres (auditoría histórica), sin notificar al ciudadano.
RN-02
Al abrir el seguimiento, el sistema calcula y muestra: fecha_limite_respuesta, días hábiles restantes (o días de atraso), indicador visual (verde ≥4 días, amarillo 1-3, rojo vencido).
RN-03
Tipos de seguimiento: PÚBLICA (visible en consulta ciudadana CU-07) e INTERNA (solo usuarios autenticados con permiso sobre el caso). Nunca se mezclan en la respuesta pública.
RN-04
Permisos: AGENTE solo en casos asignados; SUPERVISOR en casos de su área; ADMIN en todos. La validación es obligatoria en backend (@PreAuthorize + chequeo de ownership).
RN-05
Cada seguimiento genera un registro nuevo. No se actualizan ni eliminan seguimientos existentes. El campo avance_porcentaje del caso toma el último valor enviado (si viene informado).
RN-06
Notificación por correo solo si: tipo=PÚBLICA AND notificar=true AND es_anonimo=false AND email_ciudadano válido. El correo incluye: código, título del avance, descripción pública, estado actual, fecha. No incluye notas internas ni datos de funcionarios más allá del área.
RN-07
Todo registro, prórroga, escalamiento o intento denegado debe quedar en bitacora_casos / bitácora de auditoría con usuario, fecha, hora, IP y descripción. Bitácoras inmutables.
RN-08
Inmutabilidad del seguimiento: prohibido UPDATE/DELETE sobre seguimientos_caso. Correcciones = nuevo registro tipo CORRECCIÓN vinculado con seguimiento_padre_id.
RN-09
Plazos por tipo (días hábiles desde fecha_registro): Queja(Q)=15, Reclamo(R)=20, Denuncia(D)=30, Sugerencia(S)=30. fecha_limite_respuesta se calcula al crear el caso (CU-02) y puede prorrogarse solo por SUPERVISOR/ADMIN (FA-07).
RN-10
La consulta pública (código de seguimiento) expone únicamente: código, tipo, estado, fecha_registro, fecha_ultima_actualizacion, avance_porcentaje (opcional) y lista de seguimientos PÚBLICA (título, descripción, fecha). Sin email, teléfono, IP ni notas internas.
RN-11
El porcentaje de avance es informativo; llegar a 100% NO resuelve ni cierra el caso. La resolución formal corresponde a CU-05.
RN-12
Días hábiles: se excluyen sábados, domingos y días feriados configurados en tabla dias_no_laborables. El cálculo debe ser consistente en backend.
10. Requerimientos No Funcionales
ID
Tipo
Descripción
RNF-01
Rendimiento
Registrar un seguimiento (validación + INSERT + bitácora) ≤ 3 segundos. Carga de línea de tiempo ≤ 2 segundos con hasta 100 entradas.
RNF-02
Seguridad
Endpoints autenticados con JWT. Filtrado estricto de seguimientos públicos vs internos. Prevención de IDOR sobre caso_id.
RNF-03
Usabilidad
Línea de tiempo visual (timeline), badges PÚBLICA/INTERNA, indicador de plazo semáforo, formulario con contador de caracteres.
RNF-04
Auditoría
Cumplir TDR: registrar creación de seguimientos y descarga de evidencias; impedir modificación de bitácoras.
RNF-05
Disponibilidad
El job de detección de vencimientos (FA-08) debe ejecutarse al menos 1 vez al día (recomendado cada hora laboral).
RNF-06
Integridad
Transacción atómica: guardar seguimiento + actualizar caso + bitácora. Si falla un paso de persistencia, rollback completo. La notificación SMTP es asíncrona/post-commit.

13. Criterios de Aceptación (Definition of Done)
ID
Criterio
CA-01
Un agente puede registrar un seguimiento PÚBLICO en un caso asignado EN_PROCESO y el ciudadano lo ve al consultar el código.
CA-02
Un seguimiento INTERNO no aparece en GET público ni en el correo al ciudadano.
CA-03
No es posible editar ni borrar un seguimiento existente (API retorna 405 o 403).
CA-04
Al vencer el plazo, el caso queda escalado y el supervisor recibe notificación.
CA-05
Una prórroga válida extiende fecha_limite_respuesta y queda en bitácora con justificación.
CA-06
Un agente no puede registrar seguimiento en casos de otro agente (403).
CA-07
Si SMTP falla, el seguimiento permanece guardado y se informa el fallo de notificación.
CA-08
avance_porcentaje=100 no cambia el estado a RESUELTO automáticamente.
