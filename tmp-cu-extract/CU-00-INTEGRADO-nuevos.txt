Integración de Portal Público e Inicio de Sesión en un único CU-00
1.0

1. Introducción.
1.1. Objetivo.
El presente CU tiene como objetivo describir la interacción del ciudadano y del usuario municipal con el Portal Público del Sistema QRDS. El portal permite acceder sin autenticación al registro de quejas, reclamos, denuncias y sugerencias y a la consulta de seguimiento; además, integra el proceso de inicio de sesión para los usuarios internos autorizados.
2. Definición Caso de Uso
2.1 Actores.
2.1.1. Ciudadano / Usuario Público.
2.1.2. Usuario Municipal.
2.1.3. Sistema QRDS.
2.1.4. Servidor Web.

2.2 Precondiciones.
2.2.1. Que el servidor web y los servicios requeridos por el Sistema QRDS se encuentren activos.
2.2.2. Que la base de datos se encuentre operativa.
2.2.3. Que el Portal Público se encuentre disponible mediante HTTPS.
2.2.4. Para iniciar sesión, el usuario municipal debe contar con un usuario activo dentro de la aplicación. RN01.

2.3 Flujo Normal Básico
1. El usuario ingresa a la URL del Portal Público del Sistema QRDS.
2. El sistema carga la página principal sin requerir autenticación.
3. El sistema muestra las opciones principales:
   a. Registrar Queja, Reclamo, Denuncia o Sugerencia.
   b. Consultar Seguimiento de Caso.
   c. Iniciar Sesión.
4. El usuario selecciona una de las opciones disponibles.
5. Si selecciona “Registrar Queja, Reclamo, Denuncia o Sugerencia”, el sistema continúa en FA01.
6. Si selecciona “Consultar Seguimiento de Caso”, el sistema continúa en FA02.
7. Si selecciona “Iniciar Sesión”, el sistema continúa en FA03.
8. Fin del caso de uso.

2.4 Flujos Alternos.
FA01: Registrar Queja, Reclamo, Denuncia o Sugerencia
1. El ciudadano selecciona la opción “Registrar Queja, Reclamo, Denuncia o Sugerencia”.
2. El sistema redirige al formulario público correspondiente al CU-03 sin requerir autenticación.
3. El registro deberá cumplir las reglas aplicables al registro de casos y a la generación del identificador de seguimiento. RN03 RN04.
4. Fin del flujo alterno.

FA02: Consultar Seguimiento de Caso
1. El ciudadano selecciona la opción “Consultar Seguimiento de Caso”.
2. El sistema redirige al CU-05.
3. El ciudadano ingresa el identificador o mecanismo de consulta autorizado.
4. El sistema valida que el caso exista y muestra únicamente la información permitida para una consulta pública. RN09.
5. Si el caso no existe o la consulta no es válida, el sistema informa la situación sin exponer información restringida.
6. Fin del flujo alterno.

FA03: Iniciar Sesión
1. El usuario municipal selecciona la opción “Iniciar Sesión”.
2. El sistema despliega los siguientes campos:
   a. Usuario.
   b. Contraseña.
3. El usuario ingresa los datos correspondientes.
4. El sistema habilita el botón “Acceder”.
5. El usuario selecciona el botón “Acceder”.
6. El sistema valida que el usuario se encuentre activo, que las credenciales sean correctas y que posea un rol y permisos válidos. RN01 RN02.
7. Si las credenciales son válidas, el sistema registra el inicio de sesión en la bitácora de auditoría. RN14 RN15 RN16.
8. El sistema permite el ingreso a la bandeja principal de acuerdo con el rol y permisos asignados.
9. Fin del flujo alterno.

FA04: Credenciales inválidas o usuario inactivo
1. El sistema rechaza el acceso.
2. El sistema muestra un mensaje indicando que las credenciales no son válidas o que el usuario no se encuentra habilitado, sin revelar información sensible.
3. El sistema regresa al paso 2 de FA03.
4. Fin del flujo alterno.



FA05: Cerrar Sesión
1. El usuario autenticado selecciona la opción “Cerrar Sesión”.
2. El sistema invalida la sesión activa.
3. El sistema registra el cierre de sesión en la bitácora de auditoría. RN14 RN15 RN16.
4. El sistema redirige al Portal Público.
5. Fin del flujo alterno.

2.5 Postcondiciones.
2.5.1. El ciudadano accedió al módulo público seleccionado o el usuario municipal inició sesión correctamente.
2.5.2. Si se inició o cerró sesión, el evento quedó registrado en la bitácora de auditoría con los datos requeridos.
2.5.3. La consulta pública no expone información restringida ni modifica el caso.
2.5.4. Si la autenticación falló, no se creó una sesión válida ni se concedió acceso a funciones internas.
3. Requerimientos Suplementarios o no Funcionales
ID
Descripción
RNF-01
El Portal Público debe operar mediante HTTPS.
RNF-02
Las credenciales no deben exponerse en URL, mensajes de error ni registros visibles al usuario.
RNF-03
La interfaz debe ser responsive y permitir el acceso a las funciones públicas y de autenticación de forma clara.
RNF-04
Las validaciones de autenticación y permisos deben ejecutarse en el sistema, no únicamente en la interfaz.
RNF-05
Las bitácoras generadas por inicio y cierre de sesión deben ser inmutables desde las funciones normales de la aplicación.
